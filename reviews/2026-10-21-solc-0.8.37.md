# Solidity 0.8.37 upgrade validation

Date: 21 October 2026. Baseline: `ecb04db040fc69b967bd43c842a27150144bb5b8` (Solidity 0.8.24).

Upgrade the project's exact Solidity pragmas and `solc` development dependency to **0.8.37+commit.f401782d**. Update the lockfile and build documentation to match. Contract business logic, fixed addresses, ownership behavior and OpenZeppelin 5.3.0 remain unchanged.

## Settings and EVM target

- Optimizer enabled, 200 runs.
- EVM target: `shanghai`.
- IR pipeline disabled.
- Deployment budget: `10000000000000000000000`, or 10,000 nominal underlying units per treasury per active Votium round.

Osaka is a supported Ethereum mainnet target. A separate compilation comparison using 0.8.37, 200 optimizer runs and IR disabled found **identical executable creation and deployed runtime code** between Shanghai and Osaka after stripping compiler metadata. Each has 6,552 bytes of creation code and 6,162 bytes of deployed runtime, including metadata. Neither emits MCOPY, TLOAD, TSTORE or CLZ in the executable runtime. The target changes verification metadata, so the build keeps Shanghai explicit to reproduce the tested artifacts. Osaka was compared by compilation; the execution tests below used Shanghai.

## Completed checks

- All **29 original unit tests passed** without changing assertions; no failures, skips or cancellations. Coverage includes the eight token/route combinations, ownership transfer and deployer restrictions, roles and irreversible kill, changing rates, rounding, cap boundaries, recovery and atomic rollback.
- All **22 mainnet-fork scenarios passed with each compiler**, using the same pinned state and deterministic timestamps. The normalized validation result records were identical, including recipient rounding dust and direct-gauge leftovers.
- Both supported tokens covered all four funding routes, real Votium recovery and third-party rejection, wrong-token rollback, direct-reward top-up and expiry, conversion bounds, missing treasury approval and wrong gauge distributor rollback.
- For **both tokens, all 15 configured split recipients** received the expected warehouse credit and successfully withdrew it. This validates distribution mechanics, without independently reconciling recipient identities or weights against the loss ledger.
- Both original-source and flattened Remix artifacts deployed locally, matched their compiled runtime and passed initial owner, manager, budget, cap, route, kill and contribution-accounting checks. The deployer could not change the budget.
- Public ABI and storage layout are unchanged. The 0.8.24 baseline reproduced the previously reviewed runtime hash. Original and flattened 0.8.37 artifacts have equal executable runtime excluding compiler metadata.
- Both compiler comparison builds produced no compiler warnings.

The fork contains 20 validation scenarios plus two confirmations of the existing direct-reward residue policy. That policy was accepted on 20 October 2026 and is unchanged. These additional fork checks extend the checked-in historical fork suite with individual split recipient delivery and withdrawal.

Ethereum chain ID 1, block **26,235,731**, hash `0x63533d6b6bc6a8f0fb78348896b1cd436b3fb6546fe6b4ad5b60113a445df8ee`, timestamp 20 October 2026 18:57:11 UTC. Public data queries used the protected read-only runner; all approvals, transfers, deployments and impersonation occurred on local forks. The baseline reused cached public state. This is a comparison at the preceding readiness-review snapshot, rather than a new deployment-time state check.

The tests are scoped evidence, not formal verification or a guarantee against every possible defect. Current treasury funding permissions, dependency configuration and actual deployed bytecode still require the usual deployment and activation checks.
